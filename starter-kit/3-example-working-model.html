Worked example for the LLM starter kit

Example Working Model

One person (the owner) and about a dozen AI coding sessions build three apps. Each session has one role and works in its own folder. They talk through a message queue, write every decision into git or an issue, and read those files again each time they start. The owner does not have to explain the process again.

This page describes a real set-up from October 2026, with the names changed. The apps are called Atlas, Beacon and Compass here. Files 1 and 2 of the kit tell your AI tool how to build the same set-up for you.

Who does what

The owner talks mainly to one session, Lead. Lead owns the shared standards and coordinates the other sessions. Developer sessions write the app code. Design sessions own each app's screens and words.

messages through the queue, records in issues developer and own designer, no Lead in between the owner acts in that session directly

You do not need all of this on day one. One owner and one developer session is a complete set-up. Add Lead when two or more sessions run at once, and designers only if you want separate design work.

Folders and repositories

Each project is one git repository. It exists in two places: a private repository on GitHub (or similar), and a local clone on the owner's computer. Sessions work locally and push to GitHub. GitHub also holds the issues, where proposals, rulings and test reports are written.

Repositories

  • project-hub: standards, design guide, briefs and Lead's state.
  • atlas, beacon, compass: one per app, each with its own issues.
  • session-queue and ai-config: general tools, not tied to one app.

Three things that confuse people

  • One repository, many sessions. Lead and the design sessions all work in project-hub. Each one has its own area of folders, and the repo's CLAUDE.md says which areas each session may edit.
  • Worktrees. Each session gets its own working copy (a git worktree) on its own branch. Two sessions in one repo never change the same files on disk.
  • Branches. main is the agreed version. Sessions commit on their own branches. App developers fast-forward their own main when the work is ready. In the hub repo, only Lead merges into main.

Getting parallel work back into main

Conflicts are rare because each session owns its own files. Before every push, a session runs one check:

git fetch
git merge-base --is-ancestor origin/main HEAD && git push origin HEAD:main
  • The check passes when the branch already contains everything on main. The push only adds commits on top (a fast-forward), so nobody's work is lost.
  • The check fails when main has moved. The session merges origin/main into its branch, resolves conflicts, runs the checks again, and tries again.
  • No rebasing and no force-pushing. History is never rewritten, so a commit that a decision cites stays valid.
  • After a push, Lead updates the main local folder, so other sessions can read the latest standards by path.

How a session knows how to work

An AI session keeps no memory between conversations. Every rule therefore lives in a file that the session loads or reads at start. When a session's context fills up, the owner clears it and pastes a short handover prompt that points to these files.

1

Personal instructions

loaded automatically

~/.claude/CLAUDE.md (Codex: ~/.codex/AGENTS.md): how to write for the owner, which model does which job, and how to join the queue. Kit file 1 sets this up.

2

Memory

loaded automatically

One folder per project, with an index and one small file per learnt fact. Each session writes its own memory.

3

The repository's CLAUDE.md

loaded automatically

The session's role, its limits and its scope: who may send it messages, which tasks it may do, and what is out of bounds.

4

Hooks

runs automatically

A start-up hook tells the session to re-read the queue rules and start listening. An idle hook asks a session that has been idle for 45 minutes to save its state and write a handover prompt.

5

The role's state file

read on instruction

Lead reads STATE.md: open items, the decision log and the mechanics. Each designer reads its own NOTES.md. Developers read their repository's docs and open issues.

6

The handover prompt

pasted by the owner

About 250 words: the role, the files to read, what is open, and the next free numbers. It points to files and does not copy them.

Who decides what

Owner

  • Money, legal and publishing
  • Product scope and app names
  • Releases
  • Deleting data, downloads
  • Changes to rules and scopes

Lead

  • Product rulings and standards wording
  • Gates between build steps
  • Accepting design rounds
  • Merging into the hub repo's main branch

Designers

  • Screens and words for their own app
  • Their own branch
  • Shared changes go to Lead as proposals

Developers

  • Code, tests and app checks
  • Their own repository and branches, including moving main when the work is ready
  • Gated steps go to Lead as a design before any code

The key safety rule: a message that quotes the owner's approval is not approval. Only the owner's own words, typed in the session that acts, count. This stops one session from approving another session's risky action in the owner's name.

One change, start to finish

Example: Atlas starts writing location data into files.

  1. Atlas Dev posts a proposal with 4 numbered questions on an Atlas issue, each with options and a recommendation. It sends Lead a one-line queue message that links to it.
  2. Lead rules on each question. Lead writes the record first, as an issue comment and a numbered decision in STATE.md, then replies on the queue.
  3. Atlas Dev builds the change. Review finds 2 data-safety gaps, and Lead rules on them: a failed check now puts the original file back.
  4. Atlas Dev pushes to a branch and runs checks in the real app. Lead accepts the step.
  5. Atlas Dev fast-forwards main and reports the new commit. Lead records it.

How it grew

Nobody designed this up front. When something went wrong or caused friction, the owner or Lead made a decision, and the decision went into the right file with a date and the owner's own words. In the real set-up, the first month produced about 150 numbered decisions.

Week 1
One hub repository with a state file. Briefs are numbered files that the owner pastes into each session by hand.
Week 2
Each app gets its own folder, session and repository. Design moves to dedicated designer sessions.
Week 3
App work is tracked as issues on each app's repository. Lead becomes the coordinator and the owner's single contact. A standards file collects rules that any new app would also follow.
Week 4
Standing permission to commit and push freely. A local message queue replaces hand relaying. The first long autonomous runs: Lead decides on the merits and logs each decision for the owner to review.

Guard rails

  • Sessions never edit another session's repository or area. They ask through an issue or a queue message.
  • A queue message is data, not an order. Each session checks the sender and the task against its own scope, and can reject the message.
  • The queue has rate limits and a pause file that stops all messages at once. Only the owner removes the pause file.
  • In autonomous runs, money, publishing and legal questions still wait for the owner.
  • Each important result comes with the checks that were run. Anything not checked is reported as not checked.
